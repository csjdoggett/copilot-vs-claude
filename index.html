The same tool, built with Copilot, then Claude.

I'm a geotech, not a developer. I started building a tool with Copilot first, then rebuilt it with Claude. The clearest difference between the two shows up in how the work got saved and shared — so that's where I start.

The setup

Two work flows, split by a single date.

Everything before 18 May 2026 I did with Copilot. That's the day I started using Claude — and, as it turned out, the first day any of this work was properly saved in version control.

Copilot

Standalone Streamlit scripts that I nudged along by re-prompting. I shared them by zipping the folder — and when that stopped working, by copying the code across by hand. To run it, someone else had to install Python, tick Add to PATH, and run a batch file.

Claude

19 May 2026 → still going

An app the team installs

One desktop app with five tools and its own copy of Python built in. It installs like any other program, updates itself, and has a feedback button. Nobody needs Python installed. Adding the next tool follows a set process.

18 May I first put the old code into git on the day I started with Claude — as a single working baseline. Everything before that has no history at all. You can watch the way I worked change inside that one folder.

The workflow

The time I get back.

With Copilot the work went back and forth: ask, copy the code out, paste it into a new folder, run it, watch it break, ask again. With Claude it goes forward — and the working version stays safe while it does.

Backwards and forwards

  • ↻ Re-prompt for each change
  • ↻ Copy the code out by hand
  • ↻ Paste it into a new vN folder
  • ↻ Redo wrong turns (FastAPI, the DXF assumptions)
  • ↻ Lose a working version to a bad edit (407 → 241)

Every change was a full round trip — and some of them lost ground.

Forward, once

  • → I describe the change; it edits the code where it sits
  • → It already has the whole project in front of it
  • → We save it as a commit with a note
  • → Wrong turn? Roll it back — the good version is untouched
  • → Release it when it's ready; the history stays intact

I stop re-explaining myself and re-doing work.

How git works

What git is, and why it changed things.

Git is a version-control tool — a program that watches a project and records every change, so you can go back to any point, compare versions, and undo anything. GitHub is the website that keeps a copy of it online and lets people share it.

The short version: git saves changes, not copies.

A main line of saved changes, one change tried on a branch and merged back, with two releases tagged.

On my machine

repository

The project folder, watched by git. It remembers every version of every file.

vs a Downloads folder full of copies.

commit

A saved snapshot with a short note and a date.

vs a folder whose name is the only note.

branch

A safe copy to try something on, without touching the working version.

vs copying the whole folder and hoping.

merge

Fold a finished change back into the main version.

vs pasting files across by hand.

tag

Mark a point as a released version, like v2.4.1.

vs …_v2_3_1_patch.

diff & revert

See exactly what changed between two points, and undo it safely.

vs comparing folders by eye; losing 166 lines.

With GitHub — the shared copy online

clone

GitHub keeps the main copy online. Cloning pulls a full copy — with all its history — onto your machine.

vs emailing the whole folder around.

push

Send my latest commits up to GitHub, so the shared copy has them too.

vs no shared copy at all.

pull

Bring down changes from GitHub that I don't have yet. It's how two people stay in sync.

vs hoping you've got the newest zip.

pull request

Propose a batch of changes for review before they go into the main version. People can comment, then it gets merged.

vs changes just appearing, unchecked.

Delivery & centralisation

Before — scattered

A copy per person

A zip emailed around, or code copied across by hand, run from wherever each person saved it. Everyone on a different version, and no easy way to tell who had what.

Now — one source

One installer, in one place

A single signed installer, shared through GitHub releases, with a SharePoint zip as a backup. One version everyone's on.

The app today

What I ended up with.

Here are the tools in the app now. Click through them to see what each one does.

Failure Analysis

Slope Stability

Matches every pit-wall face to the nearest geological surface in 3D, then classifies it as bedding-controlled, rock-mass, or no valid plane — with apparent-dip reporting and a kinematic check.

Inpit + geology DXF (± BoD)→Outclassified CSV + criteria.txt (ZIP)

For: assessing structural control on bench and inter-ramp faces.

Geometry Check

Geometry

Reads a triangulated pit surface and measures bench height, bench width (berm) and face angle straight from the geometry — no Vulcan strings, no Excel workflow.

Inpit surface DXF (TIN)→Outper-bench BH / BW / face-angle CSV

For: checking a pit design against its geometry criteria.

Cross-Section Creator

Slope Stability

Cuts 2D cross-sections through Leapfrog surface meshes along the lines I choose, and exports them ready to drop straight into Slide2.

Insurface meshes + section lines→OutSlide2-ready section DXFs

For: setting up limit-equilibrium stability sections.

Downhole Plots

Logging

Builds multi-track downhole logs — lithology, weathering, FES, velocity — from borehole sample data, all lined up on one depth axis.

Inborehole sample data→Outmulti-track log figure

For: reviewing drillhole data.

Cross-Section Compare

In development & testing

Overlays current versus previous DXF surfaces — model and pit — on raw cross-section previews, so I can see how a design has moved between iterations.

Incurrent + previous DXFs→Outoverlaid section previews

For: checking how a surface has moved between model iterations.
